## 4. Normalization decisions — every one, with evidence

### 4.1 Subcategory slugs are PROPOSED, not sourced

**No source anywhere contains a subcategory slug.** The prototype renders Arabic labels only;
D-02 gives slugs for the 13 mains and none for subcategories. Every subcategory slug in
`catalog.json` carries `slug_evidence: "proposed"`.

They are deterministic hand-reviewed transliterations, held in one explicit map in the
extractor so they are reviewable in one place. **T1 may rename any of them without contradicting
evidence.** They are not owner-approved.

### 4.2 Wording variants — grid vs picker

Two grid chips are shortened forms of the picker's fuller wording. The picker is the fuller
surface, so its wording is canonical and the grid wording is retained as `source_label_ar` and
in `aliases_ar` — **the source label is preserved separately and never overwritten.**

| Grid wording | Picker wording (canonical) | Decision |
|---|---|---|
| ألماس وأحجار | **ألماس وأحجار كريمة** | same row; grid form is a display truncation |
| أقلام فاخرة | **أقلام وإكسسوارات فاخرة** | same row; picker adds `وإكسسوارات` |

### 4.3 The one row the picker uniquely reveals

`watches-jewelry` shows 5 named chips + `+1` in the grid. The picker, opened on that category,
lists **6** rows. The sixth is **`فضة`** (silver) — sourced from the picker alone, and the only
one of the 12 anonymous placeholders any view resolves.

### 4.4 No Arabic labels were merged

No two distinct Arabic labels were collapsed. `ساعات رجالية` / `ساعات نسائية` stay separate;
`لوحات` (art, paintings) and `لوحات سيارات` / `لوحات نقل` / `لوحات دراجات` (plates) stay separate
under **different parents** despite sharing a word — merging them would destroy a real auction
distinction.

### 4.5 Display counts are examples, not data

The grid renders `1,284 مزاد`, `417 مزاد`, etc. These are **prototype display examples**. They
are recorded as `display_count_example` and are explicitly **not** production auction counts.
No count is copied into `catalog.json` as a production fact.

## 5. The gap — 49 unresolved rows

### 5.1 Exactly where it is

| Parent | Named | Anonymous still unnamed |
|---|---|---|
| `vehicles` | 7 | **+2** |
| `real-estate` | 6 | **+2** |
| `electronics` | 5 | **+3** |
| `furniture` | 5 | **+2** |
| `collectibles` | 4 | **+2** |
| `watches-jewelry` | 6 | 0 *(the `+1` was resolved by the picker)* |
| all others | 26 | 0 |
| **total** | **61** | **11** |

Plus **38 rows that appear in no view at all** — not as a label, not even as a `+N` placeholder.
The grid accounts for 72 (`60 + 12`); the claimed total is 110; `110 − 72 = 38` rows have no
representation in any approved prototype.

### 5.2 Why haraj cannot close it

`haraj.com.sa/all-sections/` was read directly this session and returned **19 main sections**,
corroborating D-02's count. But it is **not usable to fill the 49**, for a reason that is about
evidence and not access:

**D-02 never records which haraj branch became which Dallal subcategory.** It records that the
list was derived from haraj plus seven Gulf auction platforms, with non-auction categories
removed. Reconstructing that selection now would mean re-deriving the owner's editorial
judgement — which branches survived the "does it sell at auction" filter, which were renamed,
which were merged — and calling the result evidence. It would be invention wearing a citation.

The page also returns its sub-sections as a **landing-page sample** (21 shortcuts, including
navigational entries like `موصى به` and `قسم غير مصنف`), not a complete branch tree, so it does
not even supply a full candidate set.

### 5.3 What would actually close it

One of these, and nothing else:

1. **The owner publishes the 110-row list** used when D-02 was written. This is the cheapest path
   and the record implies such a list existed.
2. **A per-category branch enumeration** from haraj + the four comparison platforms, **together
   with the owner's inclusion rule**, so the selection is reproducible rather than re-guessed.
3. **The owner rules that 110 was approximate**, and the canonical count becomes 61 (or whatever
   the sourced set turns out to be). The architecture doc's `exactly 13/110` proof in §8 would
   then need amending — that is a product decision, not a data decision.

**This is a genuine external evidence gate.** Per `CLAUDE.md` §8 and `TEAM.md` rule 16, filling
it from memory is the specific failure mode this project is most exposed to.

## 6. Category-field metadata

Read from the prototype's own field table for all 13 categories. **Evidence and proposal are
kept strictly separate** in `catalog.json`:

- `evidence.source_labels_ar` — the Arabic field labels, exactly as the prototype writes them.
- `evidence.optional_never_blocks_publish: true` — sourced from the prototype note
  («كلها اختيارية — ما تمنع النشر») and D-02 §4 item 2, which records it as **ANSWERED**.
- `proposed_validation_metadata` — **empty of evidence on purpose.** Field keys, types, units,
  options, and constraints appear in **no** source. They are reversible proposals for T1 and are
  labelled `PROPOSED — reversible, not owner-approved`.

Note `fashion`: D-02 §2 leaves its row as "(per the prototype's table)". The prototype supplies
it — `الماركة · المقاس · الحالة · الأصلية والملحقات` — so the gap in D-02 is closed by the
prototype, not by inference. `misc` has no extra fields («ما فيه حقول إضافية — الوصف يكفي»).

**None of these fields is an amount.** `المساحة`, `الممشى`, `عدد الخانات`, `الوزن` are quantities.
`CLAUDE.md` §4 and the `sar_amount` domain apply to `starting_price` and bids only.

## 8. T1 handoff

T1 (taxonomy schema/RLS/catalog + browse filter/picker/dynamic-field validation) inherits:

1. **`catalog.json` is the only taxonomy input.** Do not re-derive labels from the HTML.
2. **The 13 mains are final** — slugs and Arabic labels are both sourced.
3. **Subcategory slugs are yours to rename.** They are proposed, not evidence.
4. **The catalog is 61 rows, not 110.** Build the schema so rows are *data*, per D-02 §4 item 4
   (normalized tables, not a Postgres `enum` and not a `CHECK`), so the remaining rows land as
   inserts and never as a migration.
5. **`tests/taxonomy/catalog.check.mjs` fails until the gate in §5 clears.** Wire it into CI as a
   known-red evidence gate or leave it out until the count resolves — but do **not** relax
   `EXPECTED_SUBS` to make it green. `CLAUDE.md` §9: deleting a check to get a green tree is worse
   than the red build.
6. **`O1`/`O2`/`O3` must be answered by the owner before the picker and filter bar are built.**

**T1 is blocked on the §5 gate only for the claim "exactly 110".** Schema, RLS, and validation
work can proceed against 61 sourced rows, because the storage decision makes a new row an insert.
